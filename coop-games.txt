Концепция приложения coop-games

Документ проекта: концепция, архитектура, принятые решения и текущий
статус Дата обновления: 26 октября 2026 года

1. Краткое описание

coop-games — веб-приложение для групп друзей, которые хотят планировать
совместные игры, обсуждать, во что играть дальше, отмечать
индивидуальный прогресс и сохранять историю совместных прохождений.

Приложение должно помогать небольшой компании игроков: - создавать
группы и приглашать друзей; - искать участников по никнейму; - добавлять
игры в планы группы; - отдельно для каждого участника указывать интерес
к игре, рейтинг и статус прохождения; - видеть оценки других участников
в рамках одной группы; - сохранять историю завершённых игр и
фиксировать, кто именно участвовал в прохождении; - поддерживать вход
через внешних OAuth-провайдеров, в первую очередь Google, с возможностью
добавить Discord позже.

Главный принцип проектирования: текущие планы и членство в группе могут
меняться, а история совместных прохождений должна сохраняться независимо
от текущего состава группы.

2. Цели первой версии

Первая версия должна обеспечивать: 1. Авторизацию без собственного
пароля приложения. 2. Создание пользовательского профиля с уникальным
никнеймом. 3. Создание групп и управление участниками. 4. Добавление игр
в список группы. 5. Индивидуальные оценки интереса и статусы игр. 6.
Возможность просматривать оценки других участников своей группы. 7.
Безопасное управление доступом к группам. 8. Основание для добавления
истории прохождений в дальнейшем.

Не требуется реализовывать всё сразу. На текущем этапе приоритет —
корректная база данных, подключение к ней и затем авторизация.

4. Авторизация и профиль пользователя

4.1 Принцип входа

Приложение не будет хранить собственные пароли пользователей. Вход
должен выполняться через OAuth-провайдера: - сначала Google; - Discord
можно добавить позже.

Для OAuth рекомендуется использовать проверенную библиотеку, а не
реализовывать протокол вручную. В ходе обсуждения предложено
использовать Auth.js (next-auth@beta), но настройка ещё не завершена.

4.2 Email не сохраняется в собственной базе

Принято решение не хранить адрес электронной почты в таблице User.
Приложение будет идентифицировать пользователя через внутренний ID и
связь с внешним OAuth-аккаунтом.

В таблице OAuthAccount предполагаются: - provider — название провайдера,
например google или discord; - providerAccountId — идентификатор
аккаунта у этого провайдера; - userId — ссылка на внутреннего
пользователя приложения.

provider и providerAccountId сами по себе обычно не являются секретами,
позволяющими войти в аккаунт. Однако они всё равно являются
пользовательскими идентификаторами и не должны публиковаться без
необходимости. Сессионные токены, OAuth access/refresh tokens и секреты
подключения нужно защищать особенно тщательно.

4.3 Связывание провайдеров

Один внутренний User может иметь несколько OAuthAccount — например,
Google и Discord. Уникальность должна обеспечиваться по паре provider +
providerAccountId.

Не следует автоматически связывать два разных провайдера только потому,
что у них совпал email. Безопасный вариант: пользователь входит в
существующий аккаунт и явно подключает дополнительный провайдер из
настроек.

4.4 Создание профиля

После первого успешного входа пользователь должен выбрать свободный
никнейм. После сохранения никнейма он получает доступ к основному
приложению.

4.5 Сессии

Обсуждалось использование Auth.js с JWT-сессиями и собственным
сохранением связи OAuthAccount, поскольку стандартный Prisma-адаптер
Auth.js обычно ожидает стандартные поля и модели, в том числе email. Это
решение ещё предстоит проверить и реализовать. Нельзя считать
авторизацию настроенной до полноценного тестирования входа, выхода,
повторного входа и сохранения профиля.

5. Никнеймы

Принято решение различать никнеймы по регистру. Например, Dragon, dragon
и DRAGON могут считаться разными именами.

В текущей модели User используется: - nickname String @unique

Поле nicknameNormalized удалено по желанию владельца проекта. Приложение
не должно автоматически приводить никнейм к нижнему регистру при
сохранении или поиске, если это изменяет смысл поиска с учётом регистра.

Уникальность должна гарантироваться самой базой данных, а не только
проверкой интерфейса. Сервер должен корректно обрабатывать ситуацию,
когда два пользователя одновременно пытаются занять один никнейм.

Никнейм является отображаемым именем, а не подтверждением личности. Если
человек ещё не зарегистрировался, система не может сама знать, кому
«принадлежит» выбранный никнейм. Возможность сообщить о подражании или
изменить никнейм можно добавить позже.

6. Группы и роли

Каждая группа содержит название, создателя, текущих участников и игры,
добавленные в планы группы.

В схеме предусмотрены роли: - OWNER — владелец группы; - ADMIN —
администратор; - MEMBER — обычный участник.

Предлагаемая модель прав (окончательно ещё не реализована): - OWNER:
полный контроль над группой, управление ролями, передача владения и
удаление группы; - ADMIN: управление названием и играми, модерация
участников в рамках определённых правил, но без передачи владения; -
MEMBER: просмотр игр, выставление собственных оценок и статусов, участие
в планировании.

Право приглашать участников пока не зафиксировано окончательно: его
можно разрешить всем участникам либо только OWNER и ADMIN.

Prisma enum лишь ограничивает набор значений роли. Он не реализует права
автоматически. Все разрешения необходимо проверять в серверном коде для
каждого защищённого действия.

При создании группы создатель должен получить роль OWNER. В текущей
схеме поле GroupMember.role по умолчанию равно MEMBER, поэтому
назначение OWNER потребуется реализовать явно.

7. Игры и персональные статусы

7.1 Каталог игр

Game содержит общую информацию об игре: - title — название; - steamAppId
— необязательный уникальный идентификатор игры в Steam; - coverUrl —
необязательный URL обложки; - createdAt — дата создания записи.

Одна запись Game может использоваться в нескольких группах.

7.2 Игры внутри группы

GroupGame связывает конкретную игру с конкретной группой. Одна и та же
игра может присутствовать в разных группах, но не должна дублироваться в
одной группе. Для этого предусмотрена уникальность пары groupId +
gameId.

7.3 Индивидуальные данные

GroupGameMember хранит персональные данные конкретного участника
относительно конкретной игры в конкретной группе: - interestScore —
оценка заинтересованности; - gameRating — оценка игры; - status — личный
статус прохождения; - createdAt и updatedAt — даты создания и изменения
записи.

Оценки допускают NULL, чтобы пользователь мог ещё ничего не оценить.

7.4 Статусы

Текущий enum GameStatus: - PLANNED — запланирована; - PLAYING —
играется; - COMPLETED — участник считает игру пройденной; - DROPPED —
участник бросил игру или больше не планирует её проходить.

DROPPED не означает удаление игры из базы. Это только статус участника.

Предполагается, что статус индивидуальный: участники одной группы могут
иметь разные статусы для одной игры. Поэтому COMPLETED не означает
автоматически, что игру прошли все участники группы.

7.5 История прохождений — позднее

Идея на будущее: при изменении статуса на COMPLETED пользователь сможет
указать, кто именно прошёл игру вместе с ним, поскольку не все участники
группы обязательно проходят игру.

Данные истории должны допускать редактирование уполномоченными
пользователями. При этом история не должна зависеть от активного
членства участников в группе.

Окончательную модель истории пока сознательно не проектируем. Позже
можно добавить сущность CompletedGame и отдельную таблицу участников
прохождения. В истории стоит сохранять факт прохождения и участников,
даже если кто-то впоследствии покинет группу или сменит никнейм.

8. Выход из группы и повторное вступление

Принята предварительная концепция: - членство в группе отражает текущий
состав; - при выходе участника его личные оценки и статусы
запланированных игр не сохраняются; - сама группа и добавленные в неё
игры остаются; - история уже состоявшихся прохождений должна
сохраняться; - при повторном вступлении пользователь получает доступ к
текущим планам группы, но его старые личные статусы и оценки
автоматически не восстанавливаются.

Это решение ещё нужно реализовать в серверной логике и правилах
удаления. Удаление членства не должно каскадно удалять исторические
записи, которые будут добавлены позднее.

9. Текущая схема Prisma

Текущая схема содержит семь моделей и два enum. Она находится в
prisma/schema.prisma.

Модели: 1. User — пользователь приложения и никнейм. 2. OAuthAccount —
привязанные внешние аккаунты. 3. Group — группа. 4. GroupMember —
текущее членство и роль. 5. Game — общая запись игры. 6. GroupGame —
игра в конкретной группе. 7. GroupGameMember — личные оценки и статус
участника.

Enum: - GroupRole: OWNER, ADMIN, MEMBER. - GameStatus: PLANNED, PLAYING,
COMPLETED, DROPPED.

Основные связи и ограничения: - OAuthAccount.provider +
providerAccountId уникальны. - GroupMember.groupId + userId уникальны. -
GroupGame.groupId + gameId уникальны. - GroupGameMember.groupGameId +
groupMemberId уникальны. - User.nickname уникален с учётом регистра в
PostgreSQL при использовании обычного текстового поля. - steamAppId
необязателен, но если задан, уникален.

Важная проверка для будущей реализации: уникальность GroupGameMember не
гарантирует сама по себе, что groupMember относится к той же группе, к
которой относится GroupGame. Это нужно дополнительно проверять серверной
логикой либо продумывать дополнительное ограничение на уровне базы.

10. Как понимать связи Prisma и правила удаления

Пример: group Group @relation(fields: [groupId], references: [id],
onDelete: Cascade)

-   groupId — поле с ID связанной группы;
-   group — поле связи Prisma, через которое можно получить саму группу;
-   fields: [groupId] — поле, хранящее внешний ключ;
-   references: [id] — внешний ключ ссылается на id модели Group;
-   onDelete: Cascade — при удалении родительской группы база удалит
    записи, связанные через это отношение.

Другие правила, применённые в текущей схеме: - Cascade — удаление
зависимых записей, например членства при удалении группы; - SetNull —
при удалении пользователя, который создал группу или добавил игру,
соответствующая ссылка становится NULL, а группа или игра остаётся; -
Restrict — не позволяет удалить Game, если на неё ещё ссылаются записи
GroupGame.

Эти правила нужно проверять с учётом будущей истории прохождений.
История должна переживать выход участников из группы и, по возможности,
не должна случайно исчезать из-за каскадного удаления.

11. Техническая настройка Prisma и Neon

11.1 Prisma schema

В начале prisma/schema.prisma используется: - generator provider =
“prisma-client”; - output = “../src/generated/prisma”; - datasource
provider = “postgresql”.

Это соответствует выбранной настройке Prisma 7 с генерацией клиента в
src/generated/prisma.

11.2 prisma.config.ts

Текущая конфигурация проекта использует dotenv и определяет схему и путь
миграций, а URL берёт из переменной окружения DATABASE_URL. Не менять
конфигурацию без необходимости, если команды миграции уже успешно
работают.

11.3 Переменные окружения

В корневом .env хранится DATABASE_URL для подключения к Neon. Строка
подключения является секретом: - не помещать её в исходный код; - не
передавать в клиентский браузер; - не публиковать в Git; - убедиться,
что .env исключён в .gitignore.

Если в дальнейшем будет отдельный direct URL для миграций, его можно
настроить отдельно, но сейчас это не обязательное изменение: имеющееся
подключение уже использовалось успешно.

11.4 Prisma Client

Создан файл src/lib/prisma.ts со следующим подходом: - импорт PrismaPg
из @prisma/adapter-pg; - импорт PrismaClient из
../generated/prisma/client; - получение DATABASE_URL из process.env; -
создание PrismaPg-адаптера и PrismaClient; - переиспользование
экземпляра через globalThis в режиме разработки.

Этот модуль предназначен для повторного использования Prisma Client в
серверном коде Next.js.

11.5 Проверка подключения

Создан тестовый скрипт scripts/test-db.ts. Он загружает dotenv,
импортирует prisma из src/lib/prisma.ts, выполняет
prisma.user.findMany(), выводит количество пользователей и закрывает
соединение через prisma.$disconnect().

Пользователь подтвердил, что тест успешно выполнился. Следовательно, на
момент проверки Prisma Client мог выполнить запрос к базе Neon.

12. Команды, использованные в проекте

Установлены пакеты: - npm install @prisma/client @prisma/adapter-pg pg
dotenv - npm install -D prisma tsx @types/pg

Инициализация Prisma: - npx prisma init –datasource-provider postgresql
–output ../src/generated/prisma

Проверка схемы: - npx prisma validate

Проверка базы и генерация клиента: - npx prisma db pull - npx prisma
migrate dev –name init - npx prisma generate

Тест подключения: - npx tsx scripts/test-db.ts

Перед созданием очередной миграции всегда сначала проверить, что текущая
schema.prisma соответствует желаемой модели. Не переписывать вручную уже
применённую миграцию init. Новые изменения вносить новой миграцией.

13. Безопасность и конфиденциальность

Принятые принципы: - не хранить пароли Google или Discord; - не
сохранять email в собственной таблице User; - не раскрывать секреты
подключения и OAuth-секреты; - использовать проверенную библиотеку
OAuth; - защищать сессии и проверять авторизацию на сервере; - не
доверять userId, role или providerAccountId, переданным клиентом без
серверной проверки; - проверять права пользователя на каждое действие с
группой; - хранить минимум данных, необходимых приложению; - не
сохранять IP-адреса и историю входов без реальной необходимости; - не
автоматически объединять аккаунты разных провайдеров по совпадающему
email.

Сами provider и providerAccountId обычно не являются достаточными
данными для входа, однако их не следует считать полностью публичными.
Сессионные токены и секреты имеют гораздо более высокий уровень
чувствительности.

14. Что ещё не сделано

На момент составления документа: - схема Prisma подготовлена и содержит
семь моделей; - подключение Prisma к Neon проверено успешным запросом; -
модуль src/lib/prisma.ts создан; - тест scripts/test-db.ts успешно
выполнен; - авторизация через Google ещё не реализована; - Auth.js
обсуждался как следующий шаг, но установка и настройка не
подтверждены; - регистрация никнейма после первого входа ещё не
реализована; - серверные проверки ролей ещё не реализованы; - создание
групп, приглашения и добавление игр ещё не реализованы; - история
прохождений пока намеренно отложена; - назначение OWNER создателю группы
нужно реализовать; - ограничения на диапазоны interestScore и gameRating
пока не заданы; - правило, кто может приглашать участников и кто может
редактировать историю, предстоит определить.

15. Рекомендуемый план следующих шагов

Этап A. Завершить базу

1.  Проверить актуальную schema.prisma.
2.  Выполнить npx prisma validate.
3.  Убедиться, что миграция для актуальной семимодельной схемы применена
    к Neon.
4.  Выполнить npx prisma generate.
5.  Проверить, что схема в базе соответствует файлу Prisma.

Этап B. Авторизация

1.  Установить и настроить Auth.js.
2.  Настроить Google OAuth credentials и callback URL.
3.  Решить, как Auth.js будет работать без хранения email и со своей
    моделью OAuthAccount.
4.  Реализовать поиск или создание OAuthAccount после успешного OAuth.
5.  Создавать User только после выбора уникального никнейма.
6.  Проверить повторный вход и выход.
7.  Позже добавить привязку Discord к уже существующему User.

Этап C. Базовые функции групп

1.  Создание группы с назначением создателя OWNER.
2.  Поиск пользователей по никнейму.
3.  Приглашение и присоединение к группе.
4.  Проверка ролей на сервере.
5.  Добавление игры в группу.
6.  Создание персональной записи GroupGameMember для участника.
7.  Управление оценками и статусами.

Этап D. Правила выхода и повторного вступления

1.  Удалять текущее членство и личные данные запланированных игр при
    выходе, согласно принятому правилу.
2.  Не удалять игры группы.
3.  Обеспечить корректное повторное вступление без автоматического
    восстановления старых личных оценок.
4.  После проектирования истории прохождений гарантировать сохранность
    исторических записей.

Этап E. История прохождений

Позже спроектировать отдельную модель прохождения и список участников
конкретного прохождения. Добавить редактирование истории с проверкой
прав и сохранением истории после выхода участника из группы.

16. Основные принятые решения

1.  Проект называется coop-games.
2.  База данных — PostgreSQL в Neon.
3.  ORM — Prisma 7 с PostgreSQL-адаптером.
4.  Авторизация через OAuth, без собственных паролей.
5.  Email не сохраняется в собственной базе.
6.  Первый провайдер — Google; Discord можно добавить позже.
7.  Один User может иметь несколько OAuthAccount.
8.  Никнеймы различаются по регистру; нормализованного поля нет.
9.  В базе семь основных моделей: User, OAuthAccount, Group,
    GroupMember, Game, GroupGame, GroupGameMember.
10. Игры общие для приложения, но добавляются в планы групп через
    GroupGame.
11. Оценки и статус игры индивидуальны для каждого участника.
12. DROPPED — статус отказа от прохождения, а не удаление игры.
13. При выходе участника удаляются текущие личные данные о планах, но
    история прохождений в будущем должна сохраниться.
14. Новый участник видит текущие запланированные игры и может начать
    выставлять свои оценки.
15. История прохождений пока не реализуется, чтобы не усложнять первую
    версию.
16. Prisma Client подключается через src/lib/prisma.ts и PrismaPg.
17. Подключение к Neon уже проверено тестовым запросом.

17. Принцип дальнейшей разработки

Разрабатывать постепенно: один этап — одно понятное изменение, затем
проверка. Перед миграциями проверять схему. Не добавлять модели «на
всякий случай», пока для них нет конкретной функции. При этом
проектировать связи так, чтобы историю прохождений и новые
OAuth-провайдеры можно было добавить без полного переписывания
приложения.

Этот документ описывает концепцию и текущие договорённости, а не
утверждает, что все перечисленные функции уже реализованы. Перед
дальнейшей работой нужно сверить фактические файлы проекта с разделами о
текущем статусе.
